# Self-contained S11

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Promote plans, not worlds

A scenario can contain invented inventory, temporary policy, simulated receipts and false assumptions. Promotion extracts a selected plan and prepares it against current production evidence. Copying a final scenario database into production is prohibited.

PromotionProposal binds scenario ancestry, baseline, selected actual action/effect IDs, current target environment, granted purpose, action/schema/policy/model releases, prepared effect digest, current evidence, review, required approval and deployment constraints. Hypothetical observations are not automatically admitted production evidence. Scenario approvals, identities, grants, audit records and fake external acknowledgements cannot be imported as authoritative records.

## Lifecycle

Selected alternative → frozen scenario manifest → production re-preparation → current sentinel review if required → exact independent approval → local commitment → live dispatch → reconciliation → outcome evaluation. Changed current state, aggregate capacity, handler, recipient or permission triggers rejection or re-preparation. Competing promotions must share current reservation and predicate checks.

Definition releases follow a separate change pipeline: reproducible code build, dependency review, tests, migration rehearsal, impact analysis, approval and controlled activation. Domain edits cannot smuggle new policies, functions or agent tools into production. Builder autonomy in a branch does not grant publication rights.

## Rollout and recovery

Record activation scope, compatibility envelope, monitoring, stop condition and reversible versus irreversible effects. The proposed initial unit is a bounded action; large plans expose step boundaries. Canary sizes and operational limits are explicit approved configuration, not invented universal numbers. Restoring code cannot undo a delivery or payment. In-flight operations retain their pinned release or undergo an explicit safe migration.

## Outcome accounting

Compare predicted and observed results with actual source receipts and declared observation windows. An association between a change and a metric is not automatically causation. Keep negative outcomes and inconclusive assessments. Improvement suggestions become new ChangeSets subject to the same process; frequent human overrides do not automatically change a mandatory policy.

## Acceptance

Reject stale capacity, changed handler, wrong audience, copied grant, simulated receipt and rejected/missing-specialist release. Test a valid alternative through the actual live-style dispatcher against an isolated test receiver. Kill execution during rollout and recover in-flight work. Restore a prior software release without falsely marking irreversible effects undone. Use source PRO cases unchanged.
