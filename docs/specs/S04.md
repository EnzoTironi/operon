# Self-contained S04

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Proposed temporal convention
Subject to the preserved temporal decision gate, use half-open business-valid intervals `[from,to)` and a monotonic committed system revision. Human timestamps remain metadata; millisecond wall-clock values are not unique revision identifiers. A `WorldView` pins tenant/ontology/environment, valid-time interpretation, committed knowledge revision, definition releases, policy context and evidence coverage.

A correction at system revision k creates a new view of valid intervals without rewriting the answers to queries at knowledge revisions below k. Preserve superseded assertions and interval partitions. Point lookup, filtered sets, aggregates, links and direct/action writes must implement the same convention. Future-effective records must not appear in a current list while disappearing from current get, or vice versa.

## Storage contract
Identity keys include tenant, ontology, object type and stable object ID; environment/scenario is an additional isolation dimension. DB schema checks interval ordering, uniqueness and optimistic revision preconditions. Tombstones preserve required history without pretending that erased sensitive bytes remain available. Write plans support explicit observed-version predicates and cross-object invariant checks.

The reference PostgreSQL adapter is proposed for shared operations; SQLite uses the same contract at its supported scope. Do not expose a PostgreSQL profile based solely on generated DDL. Test driver transaction behavior, parameter binding and numeric conversions directly. Adapters cannot silently return different versions or ignore valid-time parameters.

## Queries
Separate `query.execute` from `query.explain`. Explain returns a plan and cannot count as successful retrieval. Typed Object Sets support selection, projection, link traversal, grouping, aggregates, sorting and pagination with declared consistency. Unsupported operators return a typed error, never a plausible count. Sum must sum the selected metric; field visibility applies before disclosing values or inference-sensitive aggregates according to policy.

Dynamic sets require either snapshot pinning at approval or bounded re-evaluation with explicit semantics. Predicate dependencies include absence, capacity and counts, not only object versions. Projection freshness and completeness appear in query metadata; an incomplete result must not masquerade as an exhaustive answer.

## Independent oracle
Create a small pure interval/reference-query model controlled outside implementation code. Generate operation histories with late corrections, same-clock writes, deletes, future intervals, overlap and links. Compare all adapters and entrypoints against the oracle, before and after restart. Shrink failures into stable regressions. Keep the previous six-placeholder test and CR-02/10/11; do not replace them with fresh happy paths.
