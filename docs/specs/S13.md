# Self-contained S13

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Normative specification

**Status:** proposed executable contract; source decisions remain OPEN until explicitly approved.

## Studio

Deliver model/source mapping, schema/action editing, policy authoring, saved sets, source bindings, differences between releases, impact analysis, tests, migration rehearsal and publication. AI builder output is a reviewable ChangeSet containing generated code/configuration, source evidence, assumptions, tests and compatibility notes—not a silently modified production runtime.

Construction agents operate in a builder sandbox with no production release keys. They can propose new policy but cannot approve that proposal merely because their current task benefits. Generated screens and tool schemas use the immutable definition release. Editing a display label cannot change action semantics or authority.

## Workspace

Implement organizations, teams and rooms; live object pages; data tables and filters; linked documents and discussions; evidence timelines; disputes and corrections; action proposals, approval cards; mission queues and notifications. Chat is an entrypoint, not the only interface. Human and agent operations call the same runtime.

Every card distinguishes accepted state, proposal, running operation, confirmed result and hypothetical scenario. An accepted HTTP request is not shown as completed business work. Errors provide actionable recovery without disclosing prohibited facts. The dossier shows sources, relevant releases, authorized decisions and external confirmations.

## Collaboration contract

Room membership and source permissions are authoritative records, not graph-extracted facts. The output audience is evaluated independently from requester access. Changes to membership affect subsequent chunks/notifications and queued outputs under an explicit revocation latency contract. Previously delivered content cannot be recalled by pretending a cache was cleared.

Collaborative edits require a declared conflict strategy, durable source versions and attribution. Comments or proposals cannot overwrite approved values. Publishing knowledge from a private room into a broader scope requires a governed disclosure action. The same canonical object may have several separately permissioned memory scopes.

## User-facing completeness

Include keyboard navigation, focus management, accessible state labels, clear loading/error/empty states, predictable cancellation, export, time zones, locales and audit explanations. Administrator onboarding includes company identity, connector authorization, model processor consent and rollback/export options. Provide synthetic examples not requiring paid models; live-model claims require live-model evaluation.

## Acceptance

Browser end-to-end tests create a proposal, review exact changes, confirm a receipt and inspect history. Two tenants and two room audiences remain isolated. Screen-reader/keyboard checks, interrupted sessions, concurrent edits, delayed notifications and scenario labels are evaluated. Measure task completion with users, not only pixel snapshots. Factory/agent-generated apps must pass the same contract.

## v4.2 V0 applicability — zero-UI

Permanent Studio and Workspace are post-V0. Their interaction/safety rules remain applicable to any generated interface. V0 may expose MCP Apps or dynamic/disposable/publishable generated apps, but every core workflow must have text-only CLI/MCP parity. Generated interfaces use immutable releases, preserve audience and authority, distinguish accepted/proposed/running/confirmed/hypothetical states, and may be discarded without losing canonical state.
