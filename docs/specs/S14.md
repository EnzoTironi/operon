# Self-contained S14

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Package contract
A package contains domain definitions, interfaces, actions, constraints, evidence requirements, policies, migrations, screens, queries/reports, connector mappings, fixtures and operational documentation. Installing it never grants new permissions implicitly. Exact regulated/financial policies remain domain-owner decisions; the book's teaching examples are not certified production rules.

## Required families
Collaboration/projects: ownership, tasks, commitments, dependencies, decisions and status reconciliation. Commercial/CRM: accounts, contacts, opportunities, offers, commitments and agreed transitions. Service: intake, cases, entitlements, response obligations and closure evidence. Supply/inventory: catalogs, procurement, receipts, lots, reservations, location, movement and reconciliation. Quality/documents: controlled revisions, nonconformity, investigation, corrective actions, change control, review and effectiveness. Finance: scoped accounting records, balanced posting, exact amounts, invoicing, settlement, reconciliation and close controls. Manufacturing/assets: routing, production orders, maintenance, inspections and capacity. People/qualifications: assignments, training/authorization evidence, delegation and offboarding. Governance/contracts: obligations, approvals, controlled exceptions, contract changes and attestations.

These families do not need nine separate engines. They share identity, evidence, temporal state, actions, mandates, operations and interfaces while retaining domain-specific invariants and field authority.

## Four composition journeys
J1 order to cash: accepted commitment → reserved inventory → shipment confirmation → invoice → settlement/reconciliation. J2 complaint to verified recovery: intake → affected orders/lots → investigation → controlled restriction/action → customer communication → effectiveness evidence. J3 join to revoke: source identity → qualification → bounded grant → work → revocation or explicit handover. J4 need to application: requirement → candidate definitions/code → independent tests → migration/release → observed improvement.

Each journey runs against real qualified services and isolated external receivers. It includes concurrent edits, stale data, revoked authority, failures, retries and outcome verification. A demonstration that only populates object types cannot satisfy the package claim.

## Replacing an incumbent
Coexist initially where appropriate; replacement authority is explicit. Reconcile records, historical references and access. Define which source owns each field before, during and after cutover. Fence the old writer, shadow the new process, compare outcomes, migrate in-flight work, test recovery and preserve export. Bidirectional sync without an authority rule is not a source of truth.

## Release qualification
A product may ship a subset, but must name that subset. Maximum ambition retains all families as backlog obligations. Record supported jurisdictions, business process boundaries and required domain approval. Do not claim ERP/QMS equivalence solely from generic platform acceptance or the three educational domains.

## v4.2 V0 applicability — generic kernel and recipes

The generic kernel ships before complete enterprise-family packages. Domain knowledge is delivered as versioned skills/recipes containing examples, mappings, tests, cautions and provenance. A recipe is guidance and reusable definition material, never authority. Nine-family completeness and integrated enterprise journeys remain post-V0 constitutional obligations.
