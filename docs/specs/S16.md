# Self-contained S16

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Decision capsule (normative in this document)

- D16: V0 is CLI/MCP-first, agent-agnostic and has no permanent UI; both public OSS and private real-company proof gates are mandatory.
- D-CONS-06: execute V0-A protocol/state, V0-B authoring, V0-C ingestion/provenance, V0-D reconciliation/mirror, V0-E safe use/action/views, then F1/F2.
- D-CONS-04: demo, maintenance, production and external-agent profiles are distinct; a client cannot mint identity or authority.
- D-CONS-01: canonical terms are TaskMandate, IntentGrant, WorldView, PreparedAction, DefinitionRelease and ChangeSet.
- D-CONS-02: SQLite is the durable local/benchmark profile; Node/PostgreSQL is the real-company reference profile; evidence never transfers between profiles.
- D15: V0 executes bounded registered actions only; larger plans and missions are post-V0.
- D05 engineering default: business results are exactly ALLOW, DENY, REVIEW_REQUIRED or EVIDENCE_INSUFFICIENT; infrastructure failure is a separate channel. Changing this requires a versioned decision and migration.
- D01-D04 are recipe-specific open decisions, never generic-kernel blockers. D-V0-BUSINESS-01 and D-V0-LICENSE-01 remain open and nonblocking until a commercial or public licensing claim is made. V0 OSS distribution excludes company data, hidden cases, gold outputs, private oracles, thresholds and evaluator weights.

**Status:** proposed executable contract; source decisions remain OPEN until explicitly approved.

## Profiles
Maintain explicit local-demo, local-persistent, reference-production-cell, qualified-cloud-provider and dedicated/sovereign profiles. Default production startup fails if it would use in-memory authority, a missing tenant, test credentials or a simulated dispatcher. Alchemy resources must be deployed and their bindings exercised; a manifest is evidence of configuration only.

Node/Effect/PostgreSQL is the proposed reference cell. SQLite support must detect actual Node API availability; Node 20 does not provide `node:sqlite`. D1 cannot be assumed to support interactive transactions needed by the proposed Better Auth SCIM profile. Multiple adapters run common conformance suites plus provider-specific tests.

## Operational contracts
Publish workload, capacity, latency, recovery-point/restore objectives, revocation bounds, retention, cost and noisy-neighbor constraints before testing. No universal numbers are invented here. Include application availability, authorization outages, model/connector failure and index freshness in user-facing status. Logs carry tenant/environment/correlation without secrets or unauthorized evidence.

Backups include definitions, canonical IDs, evidence pointers, decisions, approvals, operations, grants and necessary encryption metadata under separate access controls. A restore is qualified by querying history, resuming operations and validating receipts—not merely opening a database file. Corrupt audit/state cannot be silently ignored. Recovery may hold writes pending reconciliation.

## Security operations
Use secret management, key rotation, least privilege, network segmentation, egress policy, dependency scanning, signed builds, vulnerability handling and incident runbooks. A hash chain detects certain edits only relative to a trusted checkpoint; truncation/recomputed chains require independent anchored integrity and protected retention. Cleanup acts on recorded owned resources; global process kills and broad filename globs are prohibited.

## Scaling and economics
Measure contention, queue backlog, database growth, model/tool spend, per-tenant quotas and worker failures under declared workloads. Track both infrastructure cost and human review burden. Maximum autonomy requires finite aggregate resource bounds and accountable outcome evaluation. A billing counter is not the same as a transactional mission budget.

## Qualification
Actual deployed process tests, independent requests across instances, killed workers, database outage, backup/restore, migration rollback/forward recovery, dependency compromise drills, sovereign export/import and support diagnostics. Never use production credentials or real business effects for destructive qualification; use authorized dedicated test environments and receivers.
