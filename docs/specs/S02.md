# Self-contained S02

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Responsibilities

Create one portable typed representation for objects, properties, links, functions, queries, actions, policies and presentation metadata. The existing schema and SDK vocabulary is retained where its semantics fit. JSON/YAML is an authoring representation; executable meaning resides in a versioned intermediate representation and reference interpreter.

## Contract

A `DefinitionRelease` includes stable identity, revision, canonical digest, dependencies by digest, declared effect classes, schema versions, migrations and registered handler digests. Decimal amounts and units cannot silently become binary floating-point measurements; locale, time zone and currency conversion rules are explicit. Object identity includes tenant, ontology and type. Links have cardinality, temporal meaning, deletion and permission semantics.

The compiler rejects undefined types, invalid effects, ambiguous imports, unsafe widening and incompatible units. A module import never grants authority. Generated form, API schema, MCP tool and SDK must use the same immutable definition. Wire validation remains mandatory even when callers use a generated TypeScript SDK.

A `HandlerRef` resolves a reviewed immutable artifact, not a mutable function captured by an approval. Publishing under the same name never changes an existing approved operation. Dynamic code extensions cannot run in the trusted API process. Only handlers registered for the action's declared effect contract may commit.

## Lifecycle

Draft → validated candidate → independent review → published → deprecated. Rejection cannot merge. Required specialist review is evaluated on the actual publication path, not only in a helper. Historical objects and decisions keep the definition release they used; a new schema does not retroactively reinterpret them. Migrations carry forward/backward compatibility rules, mixed-version behavior and interruption recovery.

## APIs and records

Proposed services: `DefinitionRegistry.resolve(ref)`, `Compiler.compile(document)`, `ReleaseService.propose(changeSet)`, `ReleaseService.publish(approvedRelease)`. Resolve is read-authorized; publish is a control-plane action. `ObjectSetDefinition` is a reusable typed query, with a release digest and either a pinned membership snapshot or an explicitly dynamic selection. Approval semantics must state which membership is bound.

## Acceptance

Differential tests compare compiled execution to an independently controlled interpreter. Round trips preserve meaning and digests. Deliberately invalid links, imports, units and effects are rejected; legitimate extensions compile. Changing a handler or policy after review invalidates dependent approval. Generated UI/API/MCP contracts must reject the same invalid input and accept the same valid input. Migration trials include historical queries and operations queued under older releases.

Sources: product SCH/REL/MOD/API/GOV; FULL-001–004; WS-01; CR-09. The shared IR design is a proposed consolidation, not a claim that code generation already exists in full.

## v4.2 V0 amendment — public authoring

V0 exposes one public authoring state machine through shared services for CLI and MCP: definition artifact → validated candidate ChangeSet → inspect/diff → proposal → independent review → immutable publication. A single apply request may contain object/property/link types, queries, actions, policies, freshness rules and presentation metadata. Population is atomic. Importing a module or recipe never grants authority. Consumer credentials cannot author; builder credentials cannot read/write production business data or self-approve.
