# Self-contained S18

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Two explicitly separate modes

`operon demo ...` may use synthetic identities, seeded records and simulated adapters. `operon` production/remote operations use authenticated credentials and server-issued scope. A flag cannot declare `type=user`, a role or agent tier for production. Direct `object put` is either an explicitly privileged maintenance operation with audit or a demo-only path, never a general agent backdoor.

## Command contract

Parse all flags once using a strict schema. Reject unknown flags, missing values, invalid numbers, non-finite times and unsupported modes. `--help` and package scripts are generated/tested against actual command names. `--json` emits one versioned result envelope on stdout for success and expected failure; diagnostics go to stderr. Use argv subprocess execution, not interpolation into a shell.

A proposed result contains schema version, run/operation ID, command, profile/environment/scenario, result state, observations and evidence references. Establish documented exit codes for success, usage, denied/not-ready, failed assertion, blocked environment and internal failure. A blocked prerequisite is non-success for a release gate but not mislabeled as a product defect.

## Shared state and read-after-write

Persistent profile commands resolve the same qualified store for objects, proposals, audit, OMS and operations. No best-effort JSON sidecar may claim authoritative persistence. Corruption is quarantined with an explicit recovery state. Unknown action releases fail restoration; no fallback action is selected. A process crash, concurrent writers and restart are acceptance conditions.

`object query` executes a historical query and returns rows plus WorldView; `object explain` returns SQL/plan. `action preview` runs the preparation contract and records which checks executed; it produces no business writes, seeds or live effects. `model repeatability` reports sampled observations, positive iteration bounds and configuration—not formal determinism or security isolation.

## Verification harness

Launch isolated test state with a recorded run ID; inspect actual installed toolchain; execute real CLI subprocesses; validate every JSON envelope and expected business state; read state through an independent path; capture exit/stderr; enforce timeouts; retain all artifacts with hashes. A failed or malformed output cannot reach an 'all verified' banner. Every claimed feature needs actual assertions; invoking doctor, printing SQL or creating one branch does not establish transactions, time travel or reviewed publication.

Cleanup uses recorded child PIDs/process groups and exact owned paths under a unique test root. Never use global `pkill` or glob every `.db` in the repository. Preserve evidence outside destructive workspaces. Skill documentation is generated from or checked against the command registry and includes the currently unavailable profiles.

## Acceptance

The independent helper probes in this review reproduce false success for failed JSON, false success for malformed JSON, and deletion of an unrelated disposable database. A child nonzero exit correctly fails the helper. Add real CLI round trips, dual-process races, corrupt/missing state, strict flags, input sensitivity, zero iterations, authenticated approval, true dry-run state checks, actual MCP initialize/list/call/close and SQLite history. Nine current CLI tests largely assert exit codes and do not close these obligations.
