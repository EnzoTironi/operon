# Self-contained S07

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Prepare before execution

`Action.prepare` validates wire input, resolves the immutable action release, collects an authorized WorldView, checks current policy/readiness and produces a PreparedAction. It contains normalized parameters, object revisions, predicate dependencies, evidence closure, requested effects, intended recipients, usage reservations needed, and expiry. It may describe a need for review without performing business writes or live side effects.

Preview is not merely schema validation. Its envelope clearly labels which checks ran and which need execution-time revalidation. Preparation cannot obtain a credential that lets an agent bypass commit. Executable extensions are constrained to declared effects; handlers cannot hide a notification or payment outside the plan.

## Proposal and approval lifecycle

Proposal: prepared → pending review → approved/rejected/expired/superseded. ApprovalRecord binds reviewer identity and assurance, prepared-action digest, exact viewed bundle, action/schema/policy releases and applicable evidence. A sentinel recommendation never satisfies a human-specific review requirement. Independently delegated release services may approve only when policy explicitly permits them.

Proposal state and executable plans are immutable durable records, not private mutable maps serialized best-effort on process exit. Unknown action IDs or incompatible releases during restoration are rejected and quarantined, never replaced by another registered action. Changed parameters, handler, recipients or material evidence invalidate dependent approvals.

## Effect and concurrency semantics

Constructing an Effect must not claim or consume a proposal. Executing it performs a compare-and-set in the unit of work. Re-running the same Effect or delivering the same request cannot execute twice. Independent reviewers and process restarts see consistent proposal state. Approval consumption, operation identity, local changes, decision and outbound intent commit together.

The commit service revalidates permission epochs, expiry, object revisions and aggregate predicates. It does not keep a database transaction open while waiting for humans or models. A previously acceptable plan may now require re-preparation. A typed conflict is different from a successful execution and from denial.

## Rejection and explanation

Rejection preserves reviewer authority, reason visibility and proposal identity. Optional exception handling is a named policy-governed action; CLI `--override` text does not create an exception. Returning a stable operation ID does not claim external completion. UI, API, CLI and MCP share this exact lifecycle.

## Acceptance

Mutable input alias; swapped handler with same action ID; expiry and key rotation; re-run the returned Effect; two reviewers; malformed restore; unknown handler; audit failure; human/agent confusion; different recipients; cross-object capacity race; actual publication path. Positive control: an unchanged, authorized approval commits once and is explainable after restart.
