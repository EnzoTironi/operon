# Self-contained S05

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Boundary
Better Auth is proposed as identity and protocol infrastructure. It is not installed in the current candidate. Operon remains responsible for operational authorization. Qualify exact core and separately versioned plugins before integration. The earlier 1.7.4 candidate is preserved as a proposal, not asserted to be installed or compatible. Fetch documentation matching the chosen lockfile; do not apply moving `latest` examples to old plugins.

## PrincipalContext
Distinguish authenticated human, actual agent/workload, sponsoring user, delegated issuer and organization owner. Fields include issuer, subject, session/token profile, actor kind, tenant memberships, assurance, authentication time, token resource audience, permission epoch and grant references. Never derive a human reviewer from CLI tool arguments, an unverified role list or `agentSession.user` when the actual caller is an agent.

Browser sessions, ID tokens, API access tokens and agent credentials are distinct profiles. Verify issuer, audience, expiry, intended algorithm and key type. Key rotation and revocation are tested. Business endpoints using cookies need their own CSRF/origin protection. Proxy headers and tenant resolution come from a trusted deployment contract, not arbitrary request input.

## Better Auth integration
Use organizations/teams for membership projections, selected passkey/MFA/SSO flows, and SCIM only with a qualified transactional adapter. SCIM provisioning does not inherently grant Operon permissions. Directory groups map through reviewed rules, immutable identifiers and lifecycle reconciliation. Offboarding invalidates user-bound grants or triggers an explicit organization-owned mission handover.

Current official MCP guidance uses SDK v2, whereas this candidate declares SDK 1.30.0. Choose an explicit migration or isolation profile. Do not install a second OAuth provider alongside the MCP plugin. Resource-bound OAuth access is separate from the business output audience. Device authorization for the CLI is a candidate integration; it does not replace standard MCP PKCE for other clients. Agent Auth remains experimental until its concrete artifact and routes pass qualification.

## Agent routes and revocation
Default and custom capability routes must invoke the same Operon guard. Session resolution alone is not operational permission. Current security state is rechecked before sensitive operations; cached sessions and long-lived tokens cannot guarantee instantaneous revocation. Document checkpoints and propagation bounds. DPoP/shared replay checks, when selected, complement rather than replace intent/action binding.
