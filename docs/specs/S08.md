# Self-contained S08

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Local unit of work

Within one supported transactional boundary, commit business versions, decision record, approval consumption, idempotency record, aggregate usage reservation and outbound commands. None can independently report success. A compensating write to an old snapshot is not local atomicity and must not erase a concurrent writer. Check row versions and predicate dependencies under an isolation/locking strategy validated by adversarial histories.

## Operation state machine

Proposed states: PREPARED → COMMITTED → DISPATCH_PENDING → DISPATCHING → SUCCEEDED; failure alternatives include EXTERNAL_UNKNOWN, RECONCILING, FAILED, PARTIALLY_APPLIED, COMPENSATION_PENDING, COMPENSATED and COMPENSATION_FAILED. Each transition requires an event/receipt and authorized actor. A response after COMMITTED may say ACCEPTED with an operation ID; it must not claim a shipment, refund or other external result has already happened.

Idempotency keys are scoped to tenant, environment and operation kind. The same key plus same normalized payload returns the same operation. Same key plus changed payload conflicts. Provider-specific retry windows and duplicate semantics are part of the connector contract; the platform does not promise universal exactly-once external effects.

## Delivery

Outbox workers use durable ownership and fencing. A stale worker must be rejected at the protected writer, not merely asked to stop. Dispatch carries an environment-bound command, grant/checkpoint and operation identity. Scenario commands never reach a live dispatcher. A lost response leads to EXTERNAL_UNKNOWN and provider reconciliation, not blind repeat or automatic budget release.

## Recovery and compensation

A compensation is a separately authorized business action whose prerequisites and observed result matter. Some effects are irreversible. Missing compensator means non-compensable or reconciliation required; failed undo remains failed. Do not label partial execution as compensated because a cleanup callback returned or was absent.

Cancellation propagates to work not yet committed where possible. Already committed commands require their own cancellation/compensation semantics. Leases, durable workflow history and task scheduling cannot substitute for local business atomicity. Select one orchestration authority per deployment profile; qualify an Effect-native option or Temporal behind the same operation contract.

## Evaluation

Inject process death before/after each DB commit and send/ack boundary, concurrently with another writer. Restart separate processes against the actual database. Check invariant histories, outbox uniqueness, stable IDs, reservation state and truthful audit outcomes. Keep the inherited rollback-overwrites-newer-write and crash-gap cases. Test distributed locking in different processes, not two instances sharing static maps.
