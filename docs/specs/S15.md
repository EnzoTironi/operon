# Self-contained S15

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Inbound connectors

Implement stable source IDs, snapshot plus incremental-cursor capture, replay, order/outage handling, deletes, permission changes, schema drift, source freshness and checkpoint recovery. Structured records map deterministically; uncertain unstructured interpretation produces claims. Connector status must appear in evidence closure and query completeness.

A source event is idempotently processed under tenant/ontology/environment and source version. Checkpoints advance only when the intended materialization and lineage commitments are durable. Dead letters preserve enough information for authorized remediation without exposing secrets. Backpressure and rate limits are bounded and measurable.

## Outbound connectors

Each connector declares operation identity, retryability, provider idempotency behavior, authentication, timeouts, uncertainty, receipt verification, cancellation and compensation support. Token availability does not grant business authority. Credentials live in a broker/worker boundary, never the agent's filesystem. Webhooks are authenticated, replay-controlled and environment-bound.

## Federation

Organizations share contracted views and actions, not unrestricted graph access or a merged security domain. A federated contract includes authority owner, schema/release compatibility, allowed purpose, output audience, retention, validity and revocation checkpoints. A remote partner's claim remains attributed; only declared source authority can make it operationally authoritative.

Cross-cell workflows expose local commits and remote uncertainty. No global transaction is promised. Partition behavior states what can continue, what must hold and how reconciliation occurs. A counterpart cannot expand another organization's grants by relaying a signed message. Schema changes and authority transfer require negotiation and versioning.

## Portability

Export canonical definitions, allowed evidence, operational history, mappings and applicable policies using documented representations. Do not export secrets or third-party data without authority. Restore into another qualified installation and verify identity, historical answers and ongoing operations. Record inaccessible/deleted evidence honestly. Package signatures and supply-chain checks protect imports; an installed package does not grant privileges.

## Acceptance

Snapshot/CDC race, out-of-order events, duplicate webhook, lost ack, revoked connector scope, cross-tenant ID collision, source schema drift, offline cell, partner misrouting, replay and partial cutover. Test a valid federation workflow and demonstrate no prohibited data crosses the boundary. Reconcile actual source/receiver records rather than relying exclusively on Operon's own status message.
