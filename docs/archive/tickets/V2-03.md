# V2-03 - Verifiable Mission Objectives and Planning DAGs

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Requirements

1. **Verifiable Mission Objectives (`OPR-FULL-021`)**:
   - `TaskMandate`: Defines explicit issuer, owner, observable success predicates, time horizon (deadline), authority envelope, and non-negotiable stop conditions.
   - Independent Outcome Evaluator: Evaluates state and execution receipts against observable predicates.
   - Prevention of Fictional Success: If a planner/model declares mission completed but the independent evaluation finds unsatisfied predicates or pending operations, the mission status remains `PARTIAL` or `PENDING`. The model cannot self-certify success (`FULL-ACC-021`).
2. **Planning DAGs & Plan Step Validation (`OPR-FULL-023`)**:
   - Multi-step plans modeled as acyclic dependency graphs (`PlanDAG`).
   - Every step in the DAG must conform to published `TaskMandateEnvelope` (allowed action classes, object set, risk band, remaining budget).
   - Topological dependency order validation (no cycles allowed).
   - Mandatory constraint enforcement: If an optimizer/planner proposes a plan that yields a higher objective score or shorter path but violates a mandatory constraint, the plan is strictly rejected by the validator (`FULL-ACC-023`).
3. **Execution Engine & Stop Condition Enforcement**:
   - Pre-step and in-flight evaluation of stop conditions (budget exhaustion, deadline expiration, invariant violations, safety tripwire).
   - Stop condition triggers immediately halt execution and transition the mission to `STOPPED`.

## Executable tests

- `FULL-ACC-021`: Given a model declares mission completed but the operation remains pending or predicates unsatisfied; when the independent evaluator checks the state **Expected:** mission remains partial/pending without fictional success.
- `FULL-ACC-023`: Given an optimizer proposes a better result violating a mandatory constraint; when the plan passes through the verifier **Expected:** plan is rejected regardless of objective score.
- `DAG-001`: Plan DAG with circular dependencies is rejected as invalid DAG.
- `DAG-002`: Plan DAG containing an unlisted action class or unauthorized object target is rejected before execution.
- `DAG-003`: Execution halts immediately when a stop condition (budget limit, deadline, safety tripwire) is met.
- `DAG-004`: Dependent plan steps execute in valid topological order and accumulate verified execution receipts.
