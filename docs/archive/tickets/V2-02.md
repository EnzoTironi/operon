# V2-02 - Key Separation and Untrusted Model Candidates

## Program frame (normative in this document)

Operon is a zero-permanent-UI, agent-agnostic operating kernel. One kernel owns versioned contracts, identity and authority, canonical state, proposals, execution receipts, evidence and the result algebra. CLI, MCP, SDK, generated application surfaces, recipes and enterprise modules are adapters over that kernel and may not reimplement its rules.

Release order is V0 -> V1 -> V2 -> V3. V0 proves external-agent authoring, ingestion, reconciliation and safe action. V1 proves Action Inbox, exact approval, durable execution and honest outcomes. V2 adds post-V0 missions, disposable generated surfaces and the recipes/skills/module ecosystem. V3 adds federation, factory, sovereign operations and formal assurance. A later release cannot be claimed before the preceding gate passes on the same pinned candidate with independent evidence.

Current status is `SPEC_CONSISTENT_NOT_PRODUCT_PASS`: no runtime case has been executed by this dossier.

## Requirements

1. **Consumer vs Builder Key Separation (`OPR-AGT-003`)**:
   - `ConsumerKey`: Granted for runtime operational usage (reads, queries, proposals, actions within envelope).
     - Forbidden: changing ontology schemas/definitions, creating/modifying guard policies, publishing definition releases. Any definition change attempted with a consumer key is denied before execution with `KeyScopeViolationError`.
   - `BuilderKey`: Granted for ontology authoring, branch modification, running test scenarios in development sandboxes.
     - Forbidden: reading or writing production business data directly, approving or merging its own proposals/ChangeSets. Any production business data access or self-approval attempted with a builder key is denied with `KeyScopeViolationError`.
2. **Deterministic Authority over Model Candidates (`OPR-AGT-004`)**:
   - LLM and model outputs are strictly treated as untrusted candidates, never authorizations, grants, or admitted facts.
   - Prompt Injection Defense: Instructions embedded in tool results, prompt payloads, or source documents to ignore policies, approve actions, or elevate permissions are inert. Authority is evaluated by the deterministic kernel alone (`AuthorityEvaluator`).
   - Typed Candidate Admission & Quarantine:
     - Proposed actions, property updates, or claims must match registered `ObjectType` and `ActionType` definitions.
     - Nonexistent action IDs, unlisted object types, attempts to write to hidden/restricted fields, or forged safety assertions are rejected with `UntrustedCandidateQuarantinedError` and quarantined.

## Executable tests

- `AGT-003.T01`: Use a consumer key to change a guard and then invoke the newly allowed action. **Expected:** Definition change is denied before execution.
- `AGT-003.T02`: Use a builder key to read/write production business data or merge its own proposal. **Expected:** No inherited production-data or approval authority; only separately authorized reviewed operations succeed.
- `AGT-004.T01`: Inject instructions to ignore rules, approve proposals or leak secrets into a source document/tool result. **Expected:** Model behavior may vary, but the deterministic boundary prevents unauthorized admission or execution.
- `AGT-004.T02`: Return a nonexistent action/object, hidden field or safety declaration. **Expected:** Typed registry/schema/policy checks reject or quarantine the unsupported output.
